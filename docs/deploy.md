# Shared test server

One hosted copy of the backend, with its own database, so the web and mobile developers can work
against a real API instead of someone's laptop. It is for development and the demo, not production.

Two ways to run it. **Option A (Render)** is recommended: it is free, gives HTTPS (phones require it,
see below) and redeploys by itself on every push to `main`. **Option B** is any Linux server with Docker.

## What the repository already does

- `backend/Dockerfile` builds the API image. `backend/.dockerignore` keeps `.env`, `.venv` and the tests out of it.
- `backend/start.sh` runs at container start: `alembic upgrade head`, then uvicorn on `$PORT` (default 8000).
  So every deploy updates the database schema by itself.
- `GET /health` answers `{"status": "ok", "database": "ok"}`, or **503** when the database can't be reached.
  The host uses it to decide whether a new version is healthy.
- `CORS_ORIGINS` lists the web app addresses allowed to call the API from a browser.
- `postgres://` database URLs (what Render and Heroku give) are accepted, by the app and by Alembic.

## Option A: Render (recommended)

One person does this once, with their own Render account.

1. Sign up at render.com with GitHub and allow Render to read `aaskhaatt/BiletFlow`.
2. Dashboard → **New** → **Blueprint** → pick the repository. Render reads `render.yaml` from `main` and
   shows two resources: the web service `biletflow-api` and the database `biletflow-db`, both free, in Frankfurt
   (the closest region to Kazakhstan).
3. It asks for **CORS_ORIGINS**. Enter `http://localhost:5173` for now, so web developers running the
   frontend locally can call the hosted API. Add the hosted web address later, separated by a comma.
4. **Apply**. The first build takes a few minutes. When it's done, open
   `https://biletflow-api.onrender.com/health` (Render shows the exact address) and check for `"ok"`.
   The API docs are at `/docs`.
5. Share the address with the team.

`SECRET_KEY` is generated by Render and never leaves it. `DATABASE_URL` is filled in from the database.

**After that:** every merge to `main` redeploys automatically, running any new migrations. Logs, restarts
and environment variables are on the service's page in the dashboard.

**Free plan limits** (check Render's pricing page, they change):
- The API sleeps after about 15 minutes without requests; the next request wakes it, which takes up to a minute.
  Open `/health` a minute before a demo.
- The free database is deleted some weeks after it is created. Before that date, either upgrade it
  (a few dollars a month) or create a new one from the Blueprint; data on the old one is lost.

## Option B: any Linux server with Docker

```bash
git clone https://github.com/aaskhaatt/BiletFlow.git && cd BiletFlow
cp .env.example backend/.env       # if it exists yet; otherwise create backend/.env with the variables in CLAUDE.md
nano backend/.env                  # set a long random SECRET_KEY: python3 -c "import secrets; print(secrets.token_hex(32))"
docker compose up -d --build       # Postgres + API; the API applies migrations at start
curl localhost:8000/health
```

Update it with `git pull && docker compose up -d --build`. The database lives in the `postgres_data` volume and
survives rebuilds. In `docker-compose.yml` the API's `DATABASE_URL` points at the `postgres` service, whatever
`backend/.env` says.

This serves plain HTTP on port 8000. Phones need HTTPS for a non-local address (below), so put a reverse
proxy with a certificate in front of it (Caddy does this in two lines), or use Render.

## Connecting the apps

- **Mobile (Kotlin Multiplatform):** set `apiBaseUrl` in `shared/src/androidMain/.../ApiConfig.android.kt` and
  `shared/src/iosMain/.../ApiConfig.ios.kt` to the `https://` address. Android and iOS block plain `http://`
  to real servers by default, which is why HTTPS matters. Debug builds currently use the mock backend; they need
  a switch to use the real API.
- **Web:** point the API base URL at the same address, and make sure the web app's address is in `CORS_ORIGINS`.
- Errors from the API always have the body `{"error", "message", "fields"}`.

## Making someone a platform admin

There is no endpoint for this on purpose. Connect to the database (Render: the database page shows the
"PSQL Command"; Docker: `docker exec -it biletflow_postgres psql -U postgres biletflow`) and run:

```sql
update users set is_platform_admin = true where email = 'someone@example.com';
```

## Backups and recovery

SRS §7 asks for regular backups and a recovery procedure. Both are in the repository and were tested by
restoring a backup into an empty database (every table matched).

**Daily, automatic.** `.github/workflows/db-backup.yml` dumps the hosted database every night at 02:00 Kazakhstan
time and keeps each backup for 30 days (Actions tab → "Database backup" → a run → Artifacts). The repository is
public, so every backup is encrypted with AES-256 before upload. It needs two repository secrets
(Settings → Secrets and variables → Actions):

- `BACKUP_DATABASE_URL`: the database's **External** connection string (Render: the database page).
- `BACKUP_PASSPHRASE`: a long random passphrase. Keep a copy outside GitHub: without it no backup can be opened.

Until both are set, the job skips with a notice. Run it once by hand ("Run workflow") to check it.

**By hand, any time** (from `backend/`, needs Docker):

```bash
DATABASE_URL='<connection string>' ./scripts/backup_db.sh            # writes backups/biletflow-<time>.dump
```

**Recovery:**

```bash
gpg --decrypt --output biletflow.dump biletflow-<time>.dump.gpg       # only for the daily (encrypted) backups
DATABASE_URL='<connection string>' ./scripts/restore_db.sh biletflow.dump
DATABASE_URL='<connection string>' alembic upgrade head                # if the backup is older than the code
```

`restore_db.sh` replaces everything in the target database and asks you to type `yes` first. Practise on a local
database before you ever need it on the server. Backups hold emails and password hashes: `backups/` is in
`.gitignore`; never commit or share them.

## Don't

- Don't run `tests/run_all.py` against the shared database. The tests use `backend/.env`; keep that pointing
  at your own local database.
- Don't put real personal data on the test server; it is shared and its payments are simulated.
- Don't scale the API to more than one instance or worker: the expired-checkout sweeper runs inside the process.
